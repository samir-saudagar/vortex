# VORTEX Data Model

## Persistence principles

PostgreSQL is the durable source of truth. The initial design uses one database and one schema named vortex. Ownership is logical and enforced by package boundaries and service interfaces, not by separate databases. Flyway migrations are new, ordered schema definitions for this greenfield project; there is no legacy migration path.

Bag State owns the canonical bag row and state history. No other module writes bag.state or bag.current_node_id. Movement observations and command records are not authoritative bag state by themselves. Kafka retention is for delivery/recovery and inspection; REST queries read PostgreSQL.

IDs are UUIDs unless a configured value is a stable human-readable key (flightId, bagTag, nodeId, edgeId, equipmentId). Timestamps are timestamptz stored in UTC. Monetary or passenger data is not part of the model. JSONB is limited to explanation/error context and raw validated message details, not used instead of core relational fields.

## Table definitions and constraints

Names below are logical names in schema vortex. Choose SQL types/enums and exact lengths in the initial Flyway migration; constrain state values in the database as well as application code.

### flights — Flight Validation

- flight_id text primary key; stable local catalog identifier.
- carrier_code, flight_number, service_date, departure_airport, destination_airport.
- status: SCHEDULED, BOARDING, DEPARTED, CANCELLED.
- check_in_closes_at timestamptz; optional check_in_opens_at.
- created_at, updated_at.
- Unique key on (carrier_code, flight_number, service_date); index on (service_date, departure_airport, status).
- Eligibility requires a matching flight, the configured departure airport, status SCHEDULED or BOARDING, and an open check-in window: current time is at or after check_in_opens_at when configured and before check_in_closes_at. Keep local seed data deterministic relative to a documented demo clock/fixture, or use a future service date in seed data. Missing or ineligible flights are recorded as asynchronous verification failures after check-in acceptance.

### bags — Bag State and History

- bag_id UUID primary key, generated by backend.
- bag_tag text not null unique; stable scanner-facing identifier.
- flight_id text not null; intentionally not an FK.
- check_in_node_id text not null; configured initial point.
- current_node_id text not null; last known/accepted location. Initialized to check-in node; changed to a destination only by an accepted scanner observation.
- current_state text not null; finite state enum from ARCHITECTURE.md.
- current_route_id UUID nullable; deferred foreign key to the selected route if one exists.
- active_command_id UUID nullable; deferred foreign key to the command expected for the route step.
- correlation_id UUID not null unique; end-to-end workflow ID.
- state_version bigint not null; increment on each state or confirmed-node change for optimistic concurrency.
- event_sequence bigint not null default 0; per-bag outbox sequence counter updated in the same transaction as each emitted bag message.
- failure_code text nullable, failure_reason text nullable; safe concise display values. Clear only on a valid retry/progress transition.
- checked_in_at, updated_at timestamptz not null.
- Indexes on (current_state, updated_at), flight_id, current_route_id. Do not index every display field.
- Unique bag_tag prevents accidental repeated check-in of a scanner label. The state transition service performs compare-and-update using bag_id and state_version.

### checkin_requests — Bag and Check-in

- idempotency_key text primary key; required HTTP Idempotency-Key within the local application scope.
- request_hash text not null; canonical hash of the validated request body.
- bag_id UUID not null unique references bags(bag_id).
- response_status smallint not null and response_body jsonb not null; replay the same accepted response for same key/body.
- created_at timestamptz not null.
- Reuse of a key with a different hash returns 409. A duplicate bagTag under a different key returns 409. Creation of this row and initial bag/history/outbox data share a transaction.

### workflow_retry_requests — Messaging and Workflow Dispatch

- idempotency_key text primary key; required for POST /api/bags/{bagId}/retry.
- request_hash text not null; canonical hash of the accepted retry request.
- bag_id UUID not null references bags(bag_id); retry_id UUID not null unique.
- accepted_at timestamptz not null; response_body jsonb not null.
- Same key/body returns the original 202 result; same key with a different body returns 409. The retry request record and accepted workflow action share a transaction.
- Compute request_hash from HTTP method, normalized path including bagId, and canonical body so identical empty retry bodies for different bags do not collide semantically.

### bag_history — Bag State and History

- history_id UUID primary key.
- bag_id UUID not null references bags(bag_id).
- record_type: STATE_TRANSITION, WORKFLOW_RESULT, RETRY_REQUEST, or OBSERVATION_DECISION.
- previous_state text nullable, current_state text nullable; populated for state transitions.
- node_id text nullable; confirmed node at the time of record when relevant.
- reason_code text not null; safe, stable code. details jsonb nullable for limited decision context.
- event_id UUID nullable unique; message that caused the record, if any.
- route_id, command_id, observation_id UUID nullable references where available.
- state_version bigint nullable; links transition records to the bag version.
- occurred_at timestamptz (source time); recorded_at timestamptz default now() (database acceptance time).
- Index (bag_id, recorded_at, history_id), and optional index (bag_id, state_version).
- This is an append-only business timeline, not a full event-sourced aggregate log. Current bag state is a relational projection maintained transactionally with history.

### network_versions, network_nodes, network_edges — Route Planning

network_versions:
- network_version text primary key, e.g. demo-v1.
- status: DRAFT, ACTIVE, RETIRED; only one ACTIVE row enforced with a partial unique index.
- airport_code text not null; check_in_node_id text not null; created_at, activated_at.

network_nodes:
- network_version text references network_versions.
- node_id text not null; node_type: CHECK_IN, JUNCTION, SCANNER, DIVERTER, MAKEUP.
- airport_destination_code text nullable; set on makeup nodes for destination lookup.
- equipment_scanner_id text nullable foreign key to equipment.equipment_id; required for any node used as a route-step destination and required for MAKEUP.
- enabled boolean not null; display_name text not null.
- Composite primary key (network_version, node_id). Index on (network_version, airport_destination_code) for makeup lookup.

network_edges:
- network_version text, edge_id text, from_node_id text, to_node_id text, equipment_id text.
- cost integer not null check cost > 0; enabled boolean not null; optional travel_time_ms integer not null check > 0.
- Composite primary key (network_version, edge_id); composite foreign keys to source/target nodes in the same network version; equipment_id references equipment.equipment_id.
- Unique (network_version, from_node_id, to_node_id, edge_id) as needed; index (network_version, from_node_id, enabled).
- Graph validation at activation rejects missing nodes/equipment, nonpositive cost, ambiguous makeup mapping, and traversable edge targets without a scanner. Edge availability is also conditioned on equipment status at planning time.

### route_plans and route_steps — Route Planning

route_plans:
- route_id UUID primary key; bag_id UUID not null references bags(bag_id).
- route_number integer not null; monotonically increasing per bag for retries; unique (bag_id, route_number).
- status: PLANNED, ACTIVE, COMPLETE, BLOCKED, SUPERSEDED.
- network_version text not null references network_versions(network_version); source_node_id, destination_node_id text not null.
- algorithm text not null, algorithm_version smallint not null; total_cost bigint not null; planned_at timestamptz not null.
- decision_summary jsonb contains excluded edge IDs/reasons and stable tie-break explanation; avoid copying the whole network.
- Index (bag_id, planned_at desc), plus one active/latest route constraint as appropriate.

route_steps:
- route_id UUID references route_plans; step_no integer not null starting at 1.
- edge_id, from_node_id, to_node_id, equipment_id, expected_scanner_id; immutable snapshot values.
- edge_cost integer not null; optional expected_travel_time_ms.
- Composite primary key (route_id, step_no); unique (route_id, edge_id, step_no).
- The last step target equals destination_node_id. Every step target has expected_scanner_id. An empty route is valid only if source already equals makeup destination; the initial seed should avoid this case or define immediate arrival as a distinct confirmed scan requirement.
- Steps are immutable after route creation; a retry creates a new route version/route_number rather than editing the old route.

### equipment — Route Planning

- equipment_id text primary key; equipment_type: CONVEYOR, DIVERTER, SCANNER.
- status: AVAILABLE, BLOCKED, OFFLINE, MAINTENANCE; configured_enabled boolean; last_status_at timestamptz; last_report_id UUID nullable unique; safe status_reason nullable.
- Index (status, configured_enabled).
- event_sequence bigint not null default 0; per-equipment outbox sequence counter for canonical equipment-status events.
- Route Planning owns equipment catalog and availability because path calculation uses it. Movement report handling calls EquipmentStatusUpdater; it never writes this table directly. Topology contains stable equipment IDs and migrations ensure references are valid.

### route_progress — Movement Orchestration

- route_id UUID primary key references route_plans(route_id).
- bag_id UUID not null references bags(bag_id).
- next_step_no integer not null; last_confirmed_node_id text not null; active_command_id UUID nullable foreign key to movement_commands.
- status: READY, WAITING_FOR_COMMAND, WAITING_FOR_OBSERVATION, COMPLETE, FAILED, SUPERSEDED.
- observation_deadline_at timestamptz nullable; set to 30 seconds after the matching command's SUCCEEDED result is accepted and cleared only when its expected scanner observation is accepted. The timeout is configurable for local tests.
- updated_at timestamptz not null; row version for conditional update.
- Index by bag_id; partial unique index on bag_id for active progress statuses so old route progress can remain for history while one route is active.
- Index (status, observation_deadline_at) for missing-observation timeout processing.
- The row is advanced only after accepted scanner evidence. A successful command result changes command status to SUCCEEDED and the route progress to WAITING_FOR_OBSERVATION; it does not advance the confirmed node or step.

### movement_commands — Movement Orchestration

- command_id UUID primary key; bag_id, route_id references bags and route_plans; route_step_no integer not null; attempt integer not null.
- equipment_id, from_node_id, to_node_id; status ISSUED, ACCEPTED, STARTED, SUCCEEDED, REJECTED, FAILED, TIMED_OUT, SUPERSEDED. SUPERSEDED means an explicit retry activated a replacement route; late reports for the old command are retained but cannot alter current state.
- issued_at, deadline_at, started_at nullable, completed_at nullable; failure_code/reason nullable. deadline_at is 30 seconds after issue for receiving the command's terminal result; ACCEPTED/STARTED do not reset it.
- Unique (route_id, route_step_no, attempt); unique command per envelope eventId.
- Index (status, deadline_at) for timeout sweeper; index (bag_id, issued_at desc); index (route_id, route_step_no).
- Commands are durable requests and statuses, never location proof. The Python simulator keeps a local command-ID journal, outside PostgreSQL, to prevent a duplicate delivery from executing movement twice. If a journal entry is still in progress after restart, it reports an uncertain failure without a scanner observation; the bag remains at the last accepted scanner node until an explicit retry replans it. Older command reports are retained but cannot mutate the current bag once their route/command is no longer active.

### equipment_observations — Movement Orchestration

- observation_id UUID primary key; event_id UUID not null unique; bag_id, route_id, command_id references the corresponding rows.
- route_step_no, equipment_id, node_id, scanner_id, observed_at, received_at.
- decision: ACCEPTED or REJECTED; rejection_code nullable; envelope_correlation_id UUID not null.
- Optional validated_payload jsonb for diagnostic fields after size limits and redaction.
- Index (bag_id, observed_at desc), (route_id, route_step_no), (command_id).
- A new event ID repeating an existing observation_id is a business duplicate and has no state effect. Record the duplicate decision in bag_history (or a diagnostic counter), rather than inserting a second row with the same observation_id.
- Accepted observation, bag transition/history, route progress update, and next command/outbox share one PostgreSQL transaction.

### processed_events — Messaging

- consumer_name text not null; event_id UUID not null; processed_at timestamptz not null; outcome text not null.
- Composite primary key (consumer_name, event_id).
- Insert and consumer's PostgreSQL effects share one transaction. Duplicates are successful no-ops. Different consumer groups can independently process the same event.

### outbox — Messaging

- outbox_id bigint generated primary key.
- event_id UUID not null unique; event_type text not null; event_version smallint not null; topic text not null; message_key text not null; envelope jsonb not null.
- aggregate_type text not null; aggregate_id text not null; aggregate_sequence bigint not null; unique (aggregate_type, aggregate_id, aggregate_sequence).
- status PENDING, IN_FLIGHT, PUBLISHED, FAILED; attempts integer not null; created_at, next_attempt_at; claimed_until nullable; published_at nullable; last_error nullable.
- Index (status, next_attempt_at, outbox_id); index (aggregate_type, aggregate_id, aggregate_sequence).
- Business updates and outbox insert occur in one transaction. Relay marks publish after broker acknowledgement. A lease permits restart recovery. Rows are retained for a bounded local audit period before cleanup; never delete pending/failed rows.
- Aggregate sequence is assigned by incrementing bags.event_sequence or equipment.event_sequence under row lock in the same transaction. The relay does not publish sequence N+1 before N is PUBLISHED.

## Ownership and write boundaries

| Data | Owner | Writers |
|---|---|---|
| bags, bag_history | Bag State and History | BagLifecycle implementation only |
| checkin_requests | Bag and Check-in | CheckInUseCase only |
| flights | Flight Validation | Seed migrations and future flight catalog interface only |
| network_versions/nodes/edges, equipment, route_plans/steps | Route Planning | Route Planner, EquipmentStatusUpdater, and migrations only |
| route_progress, movement_commands, equipment_observations | Movement Orchestration | Movement/report handlers and migrations only |
| processed_events, outbox, workflow_retry_requests | Messaging and Workflow Dispatch | Transactional event-consumer wrapper, retry use case, and outbox publisher port/relay |

The cross-module APIs convey IDs and immutable snapshots. Do not have another module update a row through a shared repository. When a use case needs atomic changes across owners, its public application service starts one PostgreSQL transaction and calls the other module's typed method; the owner still controls the write. Avoid transactions that wait for network calls: Kafka sends happen in the outbox relay after business commit.

## Indexes, retention, and query patterns

- Primary reads: bag by bag_id; history by (bag_id, recorded_at); latest route by (bag_id, route_number); equipment by status; pending commands by status/deadline; outbox by status/next_attempt_at; processed event by consumer/event id.
- Add indexes only for observed UI/API paths. Use database pagination for history after the demo grows.
- Keep bag and state history durable for local demonstration. Retain raw observation details and outbox published records only as long as useful for debugging; define a documented cleanup task after implementation. Never purge a bag's accepted arrival history while retaining the bag.
- Do not use Kafka as a query projection or call it for REST reads.

## Migration strategy for the new project

Create Flyway migrations starting from an empty PostgreSQL database. First migration creates the schema, enum/check constraints, tables, keys, and indexes in dependency order; create the bag-to-route/command foreign keys after those target tables and mark the circular references DEFERRABLE INITIALLY DEFERRED. Follow with a separate seed migration or idempotent local seed task for flights, network version/nodes/edges, and equipment. Further migrations are append-only versioned files; do not edit a migration after it has been applied to a developer database. Test migrations both on an empty database and against the previous new-project migration version. No old schema or data is assumed.
